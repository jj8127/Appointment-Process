## 2026-10-20 제휴병원 간병 예약 요청 (로컬 구현, 미배포)

사용자 결정: 실제 제휴병원 `굿모닝한방병원 청주`(충북 청주시 상당구 무심동로 22 방서타워 2~4층)만 실데이터로 추가하고 나머지 가상 병원 12곳은 유지한다. 목표는 제휴병원 환자를 모두온 간병으로 연결하는 것이며, 핵심 지표는 요청 후 확정 피드백까지 걸리는 시간이다.

- 병원 목록은 여전히 `data/hospital-demo.ts`이다. 실제 병원은 고정 id `20000000-0000-4000-8000-000000000001`(`CARE_HOSPITAL_ID`)로 맨 앞·강조 지면에 둔다. 화면 제목의 `· 샘플`을 없애고 가상 병원에만 `샘플` 표시를 붙이며, 길찾기는 실제 병원에서만 켠다. 전화·진료 시간·병동 정보·홈페이지는 병원 홈페이지(https://gmcheongju.com/) 자료를 병원 허락을 받아 사용한다.
- 2026-10-21 사용자 결정: 병원 정보는 병원 명의 광고로 게시한다. 병원이 `docs/moduon-hospital-care/hospital-ad-confirmation.md`의 문구·사진을 승인해야 하며, 상세 표시는 `병원 제공 광고`다. 병원 승인과 정식 등록은 회사가 앱 밖에서 직접 처리하며 앱에는 반영하지 않는다(사용자 결정). 앱의 병원 정보는 `data/hospital-demo.ts`에 둔다.
- 상세의 `간병 예약 요청하기`는 `/services/care-request`로 간다. 로그인한 회원만 요청하며 희망 시작일(오늘~30일, 서버는 90일까지 허용), 간병 형태(24시간/주간)만 받는다. 2026-10-22 사용자 결정으로 연락받을 시간은 묻지 않으며, 앱은 `contactTime`을 `anytime`으로 보낸다(요청 계약·DB는 그대로). 환자 건강 정보는 별도 동의가 필요한 민감정보라 앱에서 받지 않고 상담원이 전화로 확인한다.
- 서버: `platform_hospital_care_requests` 테이블과 `create/cancel/respond_hospital_care_request_v1`. `platform-service` 동작은 `request_hospital_care`·`cancel_hospital_care`·`list_hospital_care`(본인)과 관리자 `respond_hospital_care`, `get_admin.careRequests`(회원 이름·전화 포함)이다. 예약을 받는 병원은 서버 `careHospitals` 허용 목록으로 제한한다. 같은 멱등 키 재전송은 같은 결과, 내용이 다르면 `idempotency_conflict`, 회원당 답변 대기 3건 초과는 `care_request_limit`이다.
- 상태: 접수됨 → 확인 중 → 확정 / 일정 조정 / 진행 어려움, 회원 취소. 일정 조정·진행 어려움은 회원 안내 문구가 필수이고 같은 결정 재전송은 `changed:false`이다. 확정된 요청에서만 `lib/hospital-care.ts`의 간병 시작 전 주의사항을 펼쳐 볼 수 있다. 주의사항 문구는 공개 입원 안내를 참고한 초안이며 운영자 검토 대상이다.
- 2026-10-22 사용자 결정: 병원 광고 업무(병원 광고 등록·노출 위치·광고 성과)는 앱에서 하지 않는다. `HOSPITAL_AD_ADMIN_ENABLED = false`(lib/platform-api.ts)로 제휴·정산 관리의 제휴병원 서비스 선택, 병원 제휴사 수정 행, 병원 광고 성과를 숨긴다. 코드는 지우지 않았다.
- 관리자: 제휴·정산 관리 화면 맨 위 `CareRequestAdmin`이 답변 대기 건을 첫 연락 기한 순으로 보여 준다. 2026-10-22부터 목록(답변 대기/확정/전체 탭)과 행을 눌러 여는 응답 패널로 나뉘며, 패널에서 상태 하나를 고르고 `처리하기`로 보낸다.
- 2026-10-22 화면 개편: 글자 크기는 제목 26·섹션 19·본문 16·최소 13, 주 버튼 높이 56. 아이콘은 `MaterialIcons` 채움형을 의미별 색 타일(`COLORS.tile`)에 올린다. 상태 6개의 색은 `CARE_STATUS_TONES` 하나를 회원·관리자 화면이 함께 쓴다. 상세의 `위치·길찾기`는 네이버 지도 앱(`nmap://search`)을 먼저 열고, 없으면 네이버 지도 웹을 연다. 희망 시작일은 한 달씩 넘기는 달력이다.
- 탈퇴: `platform_members.active`가 false가 되는 모든 탈퇴 경로에서 트리거가 해당 회원의 요청을 삭제한다.
- 앱 알림: 일반 회원 토큰은 `platform_member_push_tokens`(기기 토큰 1개당 마지막 등록 회원)에 저장한다. 예약 화면은 이미 허용된 기기를 조용히 등록하고, 첫 예약 요청이 성공한 뒤에만 알림 권한을 묻는다. 로그아웃은 이 기기 토큰만 지우고 탈퇴 트리거는 회원 토큰을 모두 지운다.
- 새 요청이 처음 저장되면(`created:true`, 재전송은 제외) 활성 플랫폼 관리자 중 운영 알림을 끄지 않은 사람의 `device_tokens`로 알린다. 관리자가 확정·일정 조정·진행 어려움으로 바꾸면(`changed:true`) 회원에게 알린다. 확인 중은 알리지 않는다. 발송은 응답 뒤에 실행하며 실패해도 처리 결과를 바꾸지 않는다. Expo가 등록 해제로 답한 토큰은 지운다.
- 알림 문구에는 이름·병원·건강 정보를 넣지 않는다(`_shared/hospital-care-push.ts`). 데이터는 `{kind:'hospital_care'}`이며, 앱은 알림함 대상 검증 대신 이 표시로 `/services/care-request`를 연다.
- 새 네이티브 모듈은 없으므로 앱 반영은 OTA로 가능하다. 운영 DB migration·Edge 배포·OTA 전에는 서버 동작이 없으므로 운영 앱에서 요청 전송은 실패한다. 배포는 별도 승인 대상이다.

## 2026-10-14 제휴 서비스별 추천인 (가족간병 우선)

사용자 확정 정책: 추천인은 제휴 시스템마다 따로 존재한다. 모두온 공통가입은 추천인을 받지 않으며 `platform_members.referrer_id`는 과거 기록으로만 남기고 정산에 쓰지 않는다. 이 절이 아래 '추천 관계는 모든 서비스에서 하나로 연결' 계약을 대체한다.

- 회원은 서비스마다 추천 코드 하나(`S`+11자리, 처음 공유할 때 발급)와 추천인 하나를 가진다. 지금 등록 가능한 서비스는 가족간병(`care`)뿐이다. 보험 추천인은 기존 가람in 추가정보 절차와 `fc_profiles.recommender_*`가 그대로 담당한다.
- 가족간병 소개하기는 간병 전용 코드로 `?code=…&service=care` 링크를 공유한다. 이 기능 이전에 공유된 링크(공통 회원 코드)는 가족간병에서만 계속 인정한다.
- 링크로 처음 가입하면 공통가입 화면에 코드 안내만 보이고, 가입과 함께 `register_platform_member_v2`가 간병 추천인을 원자적으로 등록한다. 쓸 수 없는 코드면 가입 전체가 되돌아가고 '추천인 없이 가입하기'로 계속할 수 있다. 인증번호 확인 뒤에만 코드를 검사한다.
- 이미 로그인한 회원이 링크를 열면 가족간병 화면에서 추천인 이름을 보고 직접 확인해 등록한다. 링크 없이 가입한 회원은 간병 신청 화면이 생길 때까지 내 정보 > 가족간병 추천인에서 코드를 입력한다.
- 처음 등록한 추천인이 확정이다. 같은 추천인 재요청은 성공으로 처리하고 다른 추천인은 `referral_already_bound`(409)로 거절한다. 본인·순환 추천은 거절한다. 관리자 변경 기능은 아직 없다.
- 신청(`create_platform_application`)은 해당 서비스의 추천인을 스냅숏하고 정산은 그 스냅숏만 사용한다.

## 2026-10-15 탈퇴 때 가람링크 직접 가입 FC 자동 정리

사용자 결정: 공통 탈퇴는 같은 번호로 가람링크에 직접 가입한 일반 FC 계정 1개를 자동으로 함께 정리한다. 탈퇴 정리 assertion에 원본 FC 번호를 서명해 보내고, 가람링크는 연결 기록이 없을 때만 그 번호의 계정이 정확히 1개이며 일반 FC·활성·설계사 아님·연결/동기화 기록 없음일 때 연결 후 정리한다. 그 외는 기존처럼 운영자 확인 보류다. 그 번호의 가람링크 계정이 아예 없으면 `no_affiliate_account`로 정리 완료 처리한다. 번호 없는 이전 assertion은 기존 동작을 유지한다.

## 2026-10-14 직원 권한 수동 부여와 단일 계정

사용자 확정 정책: 모두온 계정이 유일한 계정이며 가람in을 포함한 제휴 서비스는 그 아래에서 서비스 정보만 추가 등록한다. 관리자·본부장도 먼저 모두온에 가입하고, 제휴 서비스 직원 권한은 운영자가 수동으로 붙인다.

`grant_platform_staff_account_v1(member_id, 'admin'|'manager', staff_type, existing_account_id)`는 service_role 전용이다. 활성 공통 회원에 직원 계정을 만들거나(기존 행이 있으면 `existing_account_id`로 명시 연결) 연결하고, 공통 비밀번호 해시를 직원 계정으로 옮긴 뒤 공통 credential을 지운다. 회원의 비밀번호는 하나로 유지되며 다음 로그인부터 직원 세션이 발급된다. 이전 일반회원 토큰은 무효가 된다. 같은 요청 재실행은 `alreadyGranted`를 반환한다. FC 회원의 직원 전환은 미정 정책이므로 `fc_member_not_supported`로 거절한다.

`admin_accounts`/`manager_accounts`의 insert와 전화번호 변경은 그 번호가 다른 활성 공통 회원이면 `platform_member_phone_requires_grant`로 거절한다. 직원 행이 공통 회원 번호를 가려 직원 세션에 도달하지 못하는 상태를 막기 위함이다. 이 가드 이전에 생긴 충돌은 부여 함수의 `existing_account_id`로만 정리한다.

공통 로그인에서 가람in 계정 오류(`not_found`, `inactive_admin`, `inactive_manager`, `missing_password`, `login_unavailable`)는 각자의 문구로 표시하며 '로그인 만료'로 표시하지 않는다. 미가입 번호는 "가입되지 않은 번호입니다"를 명시한 뒤 모두온 회원가입으로 이동한다.

## 2026-10-14 일반 회원·FC의 전체 제휴 계정 탈퇴

공통 회원 탈퇴는 연결된 일반 회원·보험 FC·가람링크 계정의 개인정보와 로그인 정보를 함께 정리한다. 사용자 확인에 따라 회사 관리자·본부장과 Request Board의 현재 회사 업무 역할 계정은 유지한다. 권한 판단은 서명된 원본과 현재 DB 연결·역할을 사용한다. 요청 본문 actor/role/소속 문자열이나 전화번호 일치만으로 다른 계정을 삭제하지 않는다. 이 절이 과거 공통 탈퇴 시 FC 유지 계약을 대체한다.

withdraw_member는 confirmed:true, scope:all_affiliates, policyVersion:2026-10-14와 UUID idempotencyKey를 요구한다. 과거 delete_member 확인은 제휴 계정 삭제를 승인하지 않으므로 upgrade_required409만 반환하며 변경하지 않는다. 공통 필수 동의 버전2026-10-12를 강제로 바꾸지 않고 새 탈퇴 확인 범위를 별도로 표시한다.

접수는 공통/원본 계정 잠금과 함께 일반 FC credential·활동 권한을 중지한다. 원래 세션 SHA256 digest와 operation UUID로 소유한 요청만 재처리할 수 있다. 원문 토큰은 보관하지 않는다. Request Board는 기존 password_sync_generations의 canonical fc:UUID와 검증된 signed-generation 첫 bridge에서 원자 생성한 private fc_account_bindings만 신뢰한다. 신원 binding은 비밀번호 세대/fingerprint와 별개이며 가짜 세대를 만들지 않는다. legacy phone-only 연결은 affiliate_identity_unbound로 보류하며 추정 삭제하지 않는다. 정상 영수증은 정확한 operation/source UUID·정책·삭제 또는 검증된 독립 회사 보존 범위를 확인한다.

completed는 대상 계정과 본인 첨부 정리가 모두 확인된 상태만 의미한다. 첨부 upload token 만료 후 재정리까지 포함하고, 완료 outbox/receipt의 개인 경로를 지운다. 정리 실패나 연결 확인은 pending이며 deleted:false/cleanupPending:true를 반환한다. get_withdrawal은 원래 세션 digest로 본인 journal 상태만 읽으며 로그인/삭제를 시작하지 않는다. 앱은 화면 재진입 때 원래 요청 ID를 복구하고 조회 실패 시 새 삭제보다 다시 확인을 먼저 제공한다. 닫힌 화면의 확인창은 실행하지 않으며 검증된 완료에서만 전체 로컬 로그아웃한다. OS 재시작 후 기존 세션이 정리되면 사용자 재처리 대신 운영 authenticated worker가 계속 처리해야 한다. 이미 확정된 거래·정산·의뢰 이력은 cascade 삭제하지 않으며 개인정보가 지워진 접근 불가능한 UUID와 탈퇴 표시만 제한적으로 유지한다.

Request Board는 persisted active/token_version과 기존 runtime revoke를 재사용한다. 송수신 socket 검증과5초 idle 재검증은 이후 접근을 제한한다. 영수증 범위는 persisted_auth_and_local_runtime이며 즉각적인 전역 in-flight 회수를 보장하지 않는다. service-only withdrawal_cleanup_drain은 정확한 두 service-key 헤더 인증 뒤 최대3개 due 요청만 처리한다. 운영 예약 호출·신원 연결·legacy producer 및 모든 서버의 새 source 채택은 별도 배포 조건이며, 현재 로컬 구현을 운영 자동 완료로 표시하지 않는다.

## 2026-10-14 공통 가입·서비스 추가 등록 통합

소개 카드와 목록은 서버가 반환한 `regional_featured`/`regional_list` 영수증과 지면을 유지한다. 소개 카드는 화면과 가로 카드 영역의 교집합이 실제 카드 면적의50% 이상일 때 기존1초 노출 훅으로 집계한다. 지역 선택창이 열리면 집계를 중단한다. 병원 화면 하단 메뉴는 기존 컴포넌트의 상대 배치를 사용하여 실제 높이를 내용 viewport에서 제외한다. 글자 크기에 따른 메뉴 높이를 임의의 고정값으로 추정하지 않는다. 같은 조건 실패에서는 두 지면 자료를 보존하고 다른 조건 실패에서는 이전 자료를 숨긴다. 상세 복귀 시 필터·검색·스크롤을 유지한다.

병원 검색 목록은 키보드를 드래그로 닫지 않고 보고된 키보드 높이를 목록 아래 스크롤 여유로 더한다. 공통 로그인·가입은 기존 `KeyboardAwareWrapper`가 입력 이동을 맡는다. 제휴·정산 관리의 병원 계약·성과 입력 컴포넌트는 별도 세로 스크롤을 만들지 않으며, 상위 관리 화면이 보고된 키보드 높이를 콘텐츠 아래 여유로 더해 하나의 스크롤 소유권을 유지한다. 이 소유권은 `scripts/audit/mobile-keyboard-surfaces.json`에서 직접 화면과 공유 입력 섹션을 함께 추적한다.

병원 화면은 서비스 탐색과 정보에 집중한다. 반복 면책·경고 문구는 표시하지 않으며 광고 배지, 정보 확인일, 실제 오류/이전 조회 상태, 관리자 승인 입력과 기능 조건을 유지한다.

병원은 광고 기간·노출 위치·광고비와 구조화된 시·도 코드/시·군·구를 설정한다. 공개 지역 목록에서 선택한 지역, 병원명과 진료 분야로 검색한다. 목록은 페이지 단위로 불러오며 강조 지면과 일반 목록 모두 광고임을 표시한다. 상세는 사진·소개·주소·전화·홈페이지·운영시간·정보 확인일을 제공한다. 전화와 길찾기는 기존 외부 URL helper를 사용한다. 비회원도 조회하며 스택으로 돌아올 때 검색과 목록 위치를 유지한다.

한국 날짜에 유효한 활성 계약이고 병원이 정보/사진/문구를 승인했으며 운영자가 심의 필요 여부를 확정한 자료만 공개한다. 심의 필요 계약에는 승인 번호와 유효 종료일이 필요하다. 번호가 없거나 만료되면 노출하지 않는다. 이 기록은 운영자의 확인이며 앱의 법적 심의 판정이 아니다. 강조 지면 후보는 서버의 15분 구간에 따라 최대5개를 다시 선택하며 나머지 계약도 페이지 목록에 남는다. 노출 수 보장이나 조회 중인 화면의15분 자동 갱신을 약속하지 않는다. 실제 제휴 자료가 없어 초기 목록은 비어 있다. 참고 사이트의 병원을 실제 제휴로 복제하지 않는다.

`record_hospital_event`는 짧게 유효한 서명된 게시 영수증과 익명 세션/이벤트 UUID를 사용한다. 화면이 활성 상태에서 일정 시간 보인 광고와 상세 열람, 전화/길찾기 버튼 클릭만 기록한다. 이벤트 재전송과 세션별 반복을 제한하며 계약 revision·실제 노출 지면·한국 날짜를 보존한다. 원시 이벤트 테이블은 service-role만 접근한다. 집계는 활성 관리자만 `get_hospital_report`에서 기간·병원별로 확인한다. 이는 익명 클라이언트 신호이며 실제 통화 완료·내원·진료 매출의 증거가 아니다.

현재 보고서는 오늘 기준90일 전까지의 이벤트를 집계하고 한 요청의 기간은 최대93일, 집계 행은5000개로 제한한다. 더 큰 범위는 기간/병원 조건을 줄이도록 안내한다. 오래된 이벤트의 삭제는 정상 이벤트 수집 시 실행하며 고정 일정의 삭제 작업은 아직 없다. 정기 정리 운영과 실제 서버 수집은 출시 전에 확인한다.

병원 방문·소개 혜택은 생성하지 않는다. 보험 상담 서비스는 준비 중이며 기존 보험 수당 업무를 유지한다. 광고비·고객 연락처·환자 정보는 공개 응답과 성과 보고에 포함하지 않는다.

## 개인정보와 배포 경계

신규 테이블은 모두 RLS를 켜고 anon/authenticated 직접 접근과 RPC 실행을 회수한다. service-role은 서버에만 있다. 일반 회원 탈퇴는 이름·휴대폰·비밀번호와 관심 입력을 정리하며 UUID로 연결된 정산 이력은 남긴다. 기존 FC 탈퇴도 새 참조가 막지 않는다.

현재는 로컬 구현이다. 공통 개인정보처리방침·보유기간·기존 FC의 추가 목적 동의, 소비자 비밀번호 재설정, 실제 SMS·제휴 계약과 외부 구매 시스템은 출시 전 준비가 필요하다. 운영 DB·Edge·앱 배포와 실제 기기 검증은 이 구현의 로컬 검증과 구분한다.
